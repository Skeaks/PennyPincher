# S04 outcome, 2026-09-04

Shipped: `apps/extension` as a WXT 0.21 MV3 project (`pnpm --filter extension dev|build`).
Consent module with `CONSENT_VERSION` (stale version = no consent = re-prompt on install and
browser start), consent page with plain-language collected / not-collected / delete-everything
copy in `src/lib/copy.ts`, options page (consent status, row count, Export my data as a JSON
download, Delete my data, Withdraw consent), placeholder popup, and `src/store/` (append-only,
schema-validated, PII-key guarded, consent-gated, 5,000-row FIFO cap, serialised writes).
42 tests: consent gating, store cap, and a posture test that pins the manifest permissions and
greps every source file for `fetch`, `XMLHttpRequest`, `WebSocket`, `sendBeacon`.

What the brief got wrong: "`pnpm --filter extension dev` produces a loadable unpacked build" is
true, but the dev manifest is not the production one. WXT adds `tabs`, `scripting`, a
`localhost` host permission and an `unsafe-eval` sandbox CSP in dev only, for hot reload. The
`wxt build` output has exactly `storage` + `alarms` and the three retailer hosts, and that is
what the test pins. Anyone auditing permissions must look at `.output/chrome-mv3`, not `-dev`.

What was harder than expected: nothing structural. Small things: WXT's `UserManifest` type
rejects an `as const` manifest object, and the options page must declare
`<meta name="manifest.open_in_tab" content="true">` or its consent link and JSON download
run inside the embedded options iframe. Nothing used `alarms` yet; the permission is declared
because the brief asks for it and S06/S11 will need it.

Not done, deliberately: no browser-driven check of the consent and options pages (the pages
need extension APIs, so they cannot be opened as plain files). Jamie should load
`apps/extension/.output/chrome-mv3` unpacked once and click through before S05 builds on it.
