# Schema 1.1.0

Additive. One optional field, no change to any existing field. Written in S17 (Instacart
capture surfaces: product modal, search tiles, the probe's server-rendered HTML).

## Additive

| Change | Why |
|---|---|
| `context.fulfillmentInferred` (boolean, optional) | Instacart's server-rendered product HTML, which is what the lever probe fetches anonymously, and some listing tiles show no Delivery / Pickup control. The adapter now records Instacart's default (`delivery`) instead of failing with `no_fulfillment`, and sets this flag so the row is not mistaken for a shopper's selection. Absent or `false` means `fulfillment` was read from the page. |

## Compatibility

`schemaVersion` is a literal pin, so a 1.1.0 validator rejects `"1.0.0"` rows and a 1.0.0
validator rejects `"1.1.0"` rows. Ingest (`apps/api`) validates with the package it is built
with, so the API and the extension must be released together. There is no pilot yet (S16 has
not run) and no panelist client in the field, so no stored 1.0.0 rows need rewriting. If any
exist in D1 from deploy drills, they read as 1.0.0 rows: every 1.0.0 row is a valid 1.1.0 row
with `fulfillmentInferred` absent, and only the version literal differs.

## How to read rows

- `fulfillmentInferred: true`: the fulfilment path is the retailer's default, not a
  selection. The stats engine (S09+) should treat such rows as `fulfillment` unknown-by-page
  when attributing variance to the fulfilment lever.
- Absent or `false`: as in 1.0.0.

## Adapter provenance

Rows with `provenance.adapter` `instacart@0.2.0` or later may carry the flag. Earlier adapter
versions never set it.
