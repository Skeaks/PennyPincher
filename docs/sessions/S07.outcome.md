# S07 outcome, 2026-09-04

Shipped: `apps/api`. Hono on Workers, `wrangler.toml` with `staging` and `production` envs
and a `DB` D1 binding, no secrets. `GET /healthz` -> `{ ok, schemaVersion }`;
`POST /v1/observations` -> 400 with the full error list from `parseObservationBatch`, 201
`{ accepted, duplicates }`. Migration `0001_observations.sql`: one column per top-level field
(nested objects flattened to the parts S09/S11 will filter on), `cell_key`, `raw_json`, and an
index on `(cell_key, observed_at)`. `ObservationRepo` interface with D1 (`INSERT OR IGNORE` in
one `db.batch`, `meta.changes` summed for `accepted`) and in-memory implementations. 20 tests,
all on the memory repo, no network. Verified by hand against `wrangler dev` and a local D1:
201 then `duplicates: 1` on resend, 400 on a PII key, row present in the table.

What the brief got wrong: nothing structural. Two judgment calls worth recording. (1) The
`dev` script runs `wrangler d1 migrations apply DB --local` before `wrangler dev`, otherwise a
fresh clone serves a Worker with no table. (2) Staging and production `database_id` were
placeholders until Jamie created the D1 databases mid-session and supplied the ids; they are
now committed (identifiers, not secrets). Local dev never reads them.

What was harder than expected: the API's tsconfig uses `@cloudflare/workers-types`, not
`@types/node`, so a test could not `readFileSync` the migration to cross-check the INSERT
column list against `CREATE TABLE`. Vitest's `?raw` import (one `.d.ts` shim) does it
without Node types. Bash heredocs with `?1` placeholders and template literals did not
survive the Windows shell; files were written with the editor tool instead.

Follow-ups outside `owns:`: `biome.json` now ignores `.wrangler/` (done in #15; before that a
local `pnpm gate` after `pnpm --filter api dev` linted wrangler's build output). S08 adds the bearer token (`PILOT_TOKEN`, via `wrangler secret put`, never in the
repo) and adds `build` to `/healthz`. Mark S07 done in `docs/sessions/README.md`.
